== S1-067 | §5 | error | -

== S1-071 | §5 | error | -

== S1-072 | §5 | error | ★
> 404 | `not_found` | No such resource, or not visible to this caller
~ Reading: pay/decline/cancel by a user who is NOT a party to the request: the endpoint tables say 403 for "not the payer/requester", the generic table allows 404 for "not visible"; the probe accepts 403 or 404 for a stranger, but requires exactly 403 for the OTHER party (requester calling pay/decline, payer calling cancel). == S1-096 | §7 | idempotency | -
> Five write paths require an idempotency key (§8 and §11): **`POST /payments`**, **`POST /requests`**, **`POST /requests/{id}/pay`**, **`POST /splits`** and **`POST /settlements`**.
~ The §7 behaviours are probed as a matrix over all five paths.
== S1-097 | §7 | idempotency | ★
> The key is scoped to **the authenticated user**. Two different users may use the same key string with no interaction between them.
~ Two users, same key, different bodies: both 201, both effects happen. Same key, same body from two users is two first uses (each 201), not a replay.
== S1-098 | §7 | idempotency | ★
> A replay means the same user sending the **same method, the same path and the same body**. The same key with the same body on a different path is a different request, not a replay, and must succeed normally.
~ Same key+body to /payments and /requests (a body valid for both); same key+`{}` to /requests/A/pay and /requests/B/pay: all 201 with different resources.
== S1-099 | §7 | idempotency | -
> Header absent or empty | 400 `missing_idempotency_key`
~ Valid token and body, header absent / present-but-empty, on all five paths; no side effects.
== S1-100 | §7 | idempotency | -
> First use of the key | The normal response, **201**
== S1-101 | §7 | idempotency | ★
> Replay: same key, same body | **200**, body identical to the original response as a JSON value
~ Includes payment_id/request_id/split_id/settlement_id/created_at/committed_at identical; resources are not duplicated.
== S1-102 | §7 | idempotency | -
> Same key, different body | 409 `idempotency_key_reuse`
== S1-103 | §7 | idempotency | ★
> Key reused after the original request failed with 4xx | Treated as a first use
~ 422, 404, 403 and 409 insufficient_funds failures do not claim the key; the same key later succeeds with 201 (also with a different body).
== S1-104 | §7 | idempotency | ★
> "Same body" means the same JSON value after parsing — key order and whitespace do not matter.
== S1-105 | §7 | concurrency | ★
> For concurrent identical requests with an unused key, exactly one returns 201. The others return 200 with the same body. The operation takes effect only once.
~ 20 simultaneous identical requests on each of the five paths: one 201, nineteen 200, identical bodies, single effect (balance / counts).
== S1-106 | §7 | idempotency | ★
> A successful replay returns the original response, even after the resource changes or is cancelled. It makes no further state changes.
~ Replay of /requests after cancel returns the original body (status pending); replay of /payments after the sender was drained still 200; replay of /pay after the request is paid.
== S1-107 | §7 | idempotency | ★
> After the body has parsed as a JSON object and the caller is authenticated, an already claimed key is resolved before endpoint field validation or current-resource checks. Thus changing a successful request to an invalid body with the same key still returns `409 idempotency_key_reuse`.
